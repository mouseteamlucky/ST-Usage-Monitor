# 提示词缓存优化手册（DeepSeek 系 / OpenAI 兼容端点）

> 本文件是 ST-Usage-Monitor 的"配套方法论"：怎么读监控数字、怎么改预设把它变成钱。

## 1. 缓存怎么工作（先定模型，再谈优化）

- 提供方的"上下文缓存"是**前缀缓存**：从 **第 0 个 token 起**，逐 64 token 块比对，
  命中的部分按"命中价"计费，从第一个不同的块起全部按"未命中价"。
- 因此提示词在逻辑上被切成两段：

```text
[ 前缀区：稳定 ⇒ 命中价 ]  |  [ 分界线之后：本轮新内容 + 所有后置内容 ⇒ 全价 ]
                             ↑ 每轮都会移动
```

- **推论 1**：任何"每轮会变"的东西只要出现在前缀区，就会把它之后的**全部内容**（包括整段聊天历史）
  一起打成全价。
- **推论 2**：位于聊天历史**之后**（post-history）的内容永远是全价 —— 因为它总是排在"最新一条用户消息"之后，
  而分界线就在那里。想让它便宜，只能把它搬到聊天历史**之前**。
- **推论 3**：价差通常是 10~50 倍（deepseek-flash：命中 ¥0.02/M vs 未命中 ¥1/M），
  所以"把 1k token 从前缀区挪出去"的代价，远大于"把 1k token 搬进前缀区"的收益。

## 2. 实测案例：一个宏，55 万 token 全价

一个第三人称长篇预设，第一屏（system prompt 第一条）里带 5 个随机宏：

```text
✨ {{random::致,献给,写给}}我们{{random::最珍视的,最珍贵的,最欣赏的}}三人创作组 …
```

- SillyTavern 的 `{{random}}` 定义就是 "**will be re-rolled every time macros are resolved**"（每次解析都重掷）；
- 它位于请求的第 1 条消息、约第 347 个 token 处；
- 实测 `st-usage.jsonl`：`hit = 0 / 256 / 2048 …`，命中率 0%~8.5%（历史 27 条记录，命中 214,144 / 总 2,518,956 token）。

**修法**（三选一，按推荐度）：

1. 换成 `{{pick}}` —— 同聊天内稳定（`/reroll-pick` 可手动重掷），保留随机味道；
2. 直接写死文案；
3. 非要每轮变，就把它**挪到聊天历史之后**（尾部）—— 那里易变是免费的。

> 铁律：**聊天历史之前不许出现 `{{random}}` / `{{getvar}}` / `{{time}}` / `{{date}}` / `{{lastUserMessage}}`**。

## 3. 收益排序（按 ROI）

### ① 让前缀"常量"（最高收益，改动最小）
- 扫一遍 `chatHistory` 之前的所有条目，把每轮会变的宏全部清掉；
- 注意"看起来是常量"的坑：`{{getvar}}` 读的变量可能被脚本每轮改写；
- `{{pick}}`、`{{user}}`、`{{char}}`、静态 `{{setvar}}` 是安全的。

### ② 把静态指令搬到聊天历史之前（本例 16,691 token → 单条省 15%）
- 判据：**含易变宏的启用条目必须留在尾部**，其余（含 0 字数的分节标记、**未选中的选项**）都可以上移；
- ⚠️ **要整模块搬**：只搬"启用的条目"会把模块劈成两半（0 字标记和未选中选项留在下面），UI 结构会乱；
- 最终目标：**Chat History 之下只留"每轮必变的贴身块"**（本例：摘要 / 草稿 / 文风 / Prism×2 / User_Input /
  COT_开始 / 思考模式(繁) / Core / 尾部 共 10 条、2,854 token）。

### ③ 尾部与深度注入瘦身（每轮全价的部分）
- 尾部块（post-history）与 @depth 注入都是全价，能用"搬进前缀"解决的优先搬，搬不了的再瘦身；
- 数据库/表格类脚本注入的条目（本例 @depth2 平均 8,612 token）属"每轮都在变"，只能通过减少注入量省钱。

## 4. 怎么验证（台阶读数表）

改完发几条消息，看 `hit` 的**绝对值**（不是百分比）：

| hit 落点 | 含义 |
|---|---|
| ≈ 前缀总长 | ✅ 正常：整段前缀命中 |
| 掉一个台阶（小几百~几千） | 前缀里某条被脚本改写了（自动总结 / 世界书更新） |
| ≈ 0 ~ 几百 | 缓存命名空间切换（思考模式开关 / 模型档位）或缓存过期 |
| > 前缀总长 | 这一条是重 roll / 滑切（`payload_hash` 与上一条相同），额外复用了聊天窗口 |

用 `payload_hash` 区分"新回合"和"重 roll"后再看，命中率的"抖动"就会变成可归因的账单。

## 5. 坑位清单

1. **思考模式开关 = 换缓存命名空间**：DeepSeek 把 thinking / 非 thinking 视作不同模型实例，
   切换后第一条必然冷启动（实测 0 命中）。切换前后不要拿命中率做对比。
2. **自动总结 / 数据库脚本会重写世界书条目**：写在前缀区里的条目每次被重写都会作废一次前缀。
   能挪到 @depth（错过区）的尽量挪，或降低刷新频率。
3. **@depth 注入的深度**：depth 0~2 落在"永远全价"的尾段，代价只是那几条；depth 更大（如 10+）会毁掉中段缓存，
   让之后的整段历史重算。
4. **SillyTavern 的"双份状态"**：提示词顺序同时存在于「预设文件」和「浏览器内存」里，
   而 `settings.json` 是浏览器内存的落盘副本 —— **改文件后必须让浏览器重新加载**（预设下拉切走再切回，
   或控制台触发一次 `change`），否则下一次保存会把内存里的旧顺序写回文件。
5. **看绝对 token，不看百分比**：聊天窗口长度浮动时，同样的命中量，百分比能差 2 倍。

## 6. 测量工具

```bash
node tools/analyze.mjs --file "data/<user>/st-usage.jsonl" --prefix 37400 \
     --price-hit 0.02 --price-miss 1 --price-out 4
```

输出：逐条分类（新回合 / 重 roll / 台阶下落 / 冷启动）+ 合计命中率 + 真实花费 + 缓存省下。
